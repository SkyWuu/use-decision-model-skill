# 证据与估算

本文件的所有命令都是只读的。不要创建 issue、评论、提交或任何记录。

## 一、git 历史

过滤和截断用 git 自带的 `--grep`、`-n`，不要接 `grep`、`awk`、`head` 之类的管道。

### 先看历史是否完整

```bash
git rev-parse --is-shallow-repository   # true 表示浅克隆，历史不完整，要在报告末尾的说明里写一句
git rev-list --count HEAD               # 提交总数
git log -1 --format='%h %ad' --date=short
```

### 修复热点：被 fix / revert 提交反复改动的文件

列出提交说明像修复或回滚的提交，以及它们改过的文件，中英文说明都要匹配：

```bash
git log --no-merges -n 100 -i -E --grep='fix|bug|revert|hotfix|regression|wrong|false (positive|negative)|修复|修正|误判|漏判|误报|漏报|误杀|漏杀|回滚|撤销' --format='@@ %h %ad %s' --date=short --name-only
```

输出里反复出现的文件就是热点；同一个文件修了又撤、撤了再修，说明这个判断一直没写对。大仓库在命令末尾加 `-- <子目录>`，按子系统分批看。

### 启发式反复修改

关键词表、正则、阈值、prompt 被一改再改，说明它在近似一个语义判断：每次修一个例子，又可能弄坏另一个。

```bash
# 某个文件最近的提交
git log -n 30 --format='%h %ad %s' --date=short -- path/to/file
# 改过某个常量所在行的所有提交（-G 匹配改动的行；-S 只在出现次数变化时命中，会漏）
git log --format='%h %ad %s' --date=short -G'URGENT_WORDS' -- src/
# 某段代码的历史
git log --format='%h %ad %s' --date=short -L '/URGENT_WORDS/,+8:src/rules.py'
# 看某次修复具体改了什么
git show --stat <commit>
git show <commit> -- path/to/file
```

提交说明里的“误判 X”“漏掉 Y”“把 Z 当成……”，就是题目必须答对的边界用例，也是现成的标注数据。报告里引用一两条具体提交（短哈希加说明）即可。

报告里写“修了几次”之前，先用 `git log --oneline -- <文件>` 把提交逐条列出来再数：fix、revert、被回滚的那次提交和普通功能提交分开算。“3 次修复、2 次回滚”和“5 次修复”是不同的事实，写错了读者会怀疑整份报告。

### 没有 shell 时

`.git/logs/HEAD`（reflog）可以当普通文件读，里面有本机产生或拉取过的提交说明。全新克隆里它几乎只有一条，所以要在报告末尾的说明里写清楚覆盖了多少，不能把“没看到修复记录”当成“没有修复”。

## 二、测试、注释和文档

- 启发式函数后面跟着一长串边界测试，或一张“输入 → 期望标签”的参数化表：说明这个判断一直在被纠正；这张表也是标注数据。
- 模型输出的快照、黄金文件，说明团队对输出有明确预期。
- `evals/`、`benchmarks/`、`fixtures/`、`testdata/` 和评分代码，说明团队已经在衡量质量。

```bash
rg -n -i -e '\b(TODO|FIXME|HACK|XXX)\b.*(smart|semantic|fuzzy|heuristic|classif|dedup|duplicate|intent|relevan|similar|guess)' \
  -e '\b(TODO|FIXME|HACK|XXX)\b.*(语义|误判|漏判|误报|关键词|规则|临时|人工|更聪明|不准)' .
rg -n -i -e 'for now|temporary|good enough|best effort|rough heuristic' -e '先这样|临时方案|凑合|暂时|兜底' .
```

设计文档、ADR（`docs/adr/`、`decisions/`）、RFC、事故复盘、CHANGELOG 解释了有意为之的选择。推荐改动某个判断之前，先读它附近的这些文档：有记录的理由可能让一个看起来很好的机会变成坏主意。

## 三、现成标注

记下不需要新标注就能评估决策模型的数据：

- 测试夹具和期望输出；
- 评测集和评分代码；
- 种子数据、样例记录；
- 把自由文本映射到类别的查找表、映射表；
- 别名、同义词、黑白名单；
- 启发式规则在 git 历史里的每次修正（每次修复都是一个带标注的边界用例）；
- 数据库表结构里保存的人工改判记录（重新分类、重新打开、合并为重复）。

## 四、调用量

用每天的数量级表示：1、10、100、1k、10k、100k+ 次/天，并写出推导。需要乘除时把算式写出来（例如“300–500 单/天 × 30 天 ≈ 0.9–1.5 万单”），方便读者核对。来源优先级：

1. 文档、README、运维手册里明确写的量，引用原文位置；
2. 定时任务：周期 × 每批条数（例如每 10 分钟一批、每批 500 条 → 约 72k 条/天）；
3. Agent 循环：步数上限 × 每天运行次数（运行次数没有出处就写“上限为 每次运行 N 步，日运行次数未知”）；
4. 请求路径：调用这个判断的接口 × 文档写明的流量；只有限流或峰值配置时，写成“峰值不超过 X 次/秒（出处）”，不要自己乘成日量；
5. 每条记录判断一次：每天新增记录数（来自文档、种子数据或迁移脚本）。

只知道总量、不知道子集占比时（例如“只对海外订单判断”，但海外订单占比没有出处），写成“不超过 <总量区间的上限>（出处）”，并把占比列进测量；不要自己假设一个比例。

都推不出来就是未知，报告里不写这个数。它决定一条建议值不值得做时，把这条放进“信息不足”一节，在“待确认”里写要测什么，例如“统计 `classify()` 一周的调用次数”。

配置里的限流值、并发上限、批大小上限只是上限，不代表实际流量；引用时写明“上限”，并确认它真的被代码读取。

## 五、错判代价

分别写误判为“是”和误判为“否”的代价，以及谁来承担：

- 用户：体验变差、得到错误结果；
- 业务：钱、客服工作量、流失、合规风险；
- 数据：被悄悄污染，之后很难发现；
- 没人：只是一条建议，用户会再看。

两边代价不对称时，写明阈值应该偏向哪一边。

## 六、数据敏感度

| 级别 | 含义 | 对建议的影响 |
| --- | --- | --- |
| 无 | 代码、元数据、公开内容 | 无额外要求 |
| 内部 | 不含个人信息的业务数据 | 按公司内部数据规范 |
| 个人 | 能识别到具体个人的数据（姓名、手机号、聊天内容等） | 先用合成或脱敏数据试；确认部署方式和数据是否出域；上线前过隐私评审 |
| 受监管 | 健康、金融、未成年人、生物特征等 | 先过法务和合规；通常不适合作为第一步 |

## 七、证据强度

- **有修复记录**：git、测试、文档里能看到它出过错或被反复修改；
- **代码可见**：读代码确认这个判断存在，但没有出错记录；
- **推断**：根据结构推测，没有直接证据。

证据强度只能写这三档之一，并附出处。

## 八、多久能拿到第一次影子结果

用来挑报告开头“建议先做”的那一条：同等价值下，优先选几天就能拿到结果的。

- **几天**：判断在一个函数或接口后面，替换后结果只在一处消费；
- **几周**：需要先采集新的输入、补日志，或者结果被多处消费；
- **几个月**：需要改流程、改数据结构或先过合规。
