# 适配与复核

第 5 步按顺序用本文件：先看适合的信号，再过排除表，然后三关复核、对照能力档案。任何一关不过，候选就淘汰。

## 适合的信号

一个好候选通常具备其中大部分：

- **答案有限**：几个标签、一个是否概率、一个有序等级，或者代码能先列出候选。
- **语义模糊**：规则写不全，但懂行的人看一眼就能判断。
- **重复**：每天成百上千次，或者覆盖某类核心对象的每一条。
- **结果能直接用**：代码拿到答案就能分支、排序、过滤、路由。
- **概率有用**：有人工队列、兜底路径或可调的阈值，能按把握大小分别处理。
- **证据在手**：判断需要的信息在判断时已经存在。
- **结果可衡量**：准确率、人工审核量、延迟、成本、覆盖率等指标能前后对比。

## 排除表

主体落在下表里的，不建议交给决策模型。但很多候选可以拆：把语义部分拆出来交给模型，其余留在原处。能拆就写拆法，不能拆就移出清单。

| 情况 | 为什么不适合 | 应该怎么做 |
| --- | --- | --- |
| 算术、计数、金额比较、配额、计费 | 模型不做计算 | 代码算；结果作为状态字段或分桶传入 |
| 日期先后、时间窗、SLA、账期 | 模型把日期当文本读 | 代码算；需要从文本里认出日期时，用选择题从候选里选 |
| 精确查找、ID 匹配、格式校验、枚举映射 | 已经有确定答案 | 代码或数据库 |
| 权限、鉴权、安全边界 | 不能把授权交给概率 | 边界本身留在代码。旁边常有能做的判断：执行后检查结果是否符合意图；作为只能多拦、不能放行的额外信号；给人工审批排序 |
| 硬业务规则、合同条款、法规明文 | 规则明确且需要可审计 | 代码；规则之外的语义部分才考虑模型 |
| 生成文本、代码、摘要、计划、解释 | 决策模型不生成 | 生成式模型；决策模型可以在它之后检查或挑选 |
| 多步推理、链式推断 | 单次前向判断做不好 | 生成式模型；或拆成几道单步题，由代码组合 |
| 答案无法事先列出，代码也产不出候选 | 没有可选的选项 | 先有候选生成器，再按“从候选里选”重新评估 |
| 每天只有几次 | 接入和评估成本大于收益 | 保持现状 |
| 调用量看起来大到不现实（例如“用户 × 候选”逐对判断） | 成本和延迟扛不住 | 先别排除：看判断的属性是否随用户变化。不随用户变化的（内容质量、话题）在内容写入时判断一次存成字段，由代码按用户组合；确实随用户变化的，才按对计算调用量 |
| 已有训练好的分类器且效果达标 | 收益有限 | 保持现状；出现新标签或效果漂移时再考虑 |

## 三关复核

### 第一关：判断时证据在不在？

题目要读的字段在判断发生时是否已经存在？如果需要的输入今天没有采集（例如判断需要完整对话，但代码只存了最后一条），就把采集算进成本；采集成本决定值不值得做时，放进“信息不足”一节。

### 第二关：现在的做法是不是有意为之？

读判断点附近的注释、ADR、设计文档、提交说明。

- 有记录的理由反对改动（例如“账号封禁必须人工确认”“法务维护的条款模板不得自动改写”），就按记录调整：放弃自动化，或只做不违背记录的部分（排序、预标注、在规则之外补充判断），并在这一条里引用出处。
- 写着“临时方案”“先这样”“TODO 换成更聪明的做法”的，是加分项。

### 第三关：合规和数据约束允不允许？

- 状态里有没有个人信息、受监管数据？对照能力档案的部署方式和数据是否出域。
- 对用户的承诺、行业规定、合同约定里，哪些事必须由人决定、哪些可以自动决定？
- 判断结果会不会直接影响用户的钱、账号、内容可见性？会的话，自动执行前必须有人工或代码规则把关。

### 选择类额外一关：候选召回

“从候选里选”的上限是候选生成器的召回。模型选不到检索、正则或规则漏掉的东西。

## 对照能力档案

逐项比对。超出的改写、放进“信息不足”或淘汰；档案未填的按保守默认处理，影响所有建议的写进末尾说明：

| 检查项 | 怎么比 |
| --- | --- |
| 状态长度 | 估算状态大小（一条消息、一张工单通常很短；整段对话、长文档、几十个候选会很长）和上下文上限比 |
| 选项数 | 选择题选项数和上限比；超了改分层选择或逐个候选的是非题 |
| 等级数 | 等级题等级数和上限比 |
| 语言 | 输入以中文为主时，看中文效果是否已验证 |
| 模态 | 需要看图片时，看是否支持图片输入 |
| 部署与出域 | 和数据敏感度一起看：个人或受监管数据能不能交给模型，按第三关判断 |
| 已知弱点 | `known_weaknesses` 里命中的，改写、放进“信息不足”或淘汰 |

## 设计护栏

写决策模型的应用点时参照这些做法：

- **保留底线。** 已经在用的规则、关键词表、人工队列继续作为独立信号。模型替换的是昂贵或脆弱的部分，不是安全底线；两者结论不一致时转人工。
- **不确定区间不自动执行。** 有人工队列时，只有高于区间上沿的才自动处理，区间内都给人看。
- **永远给出口。** 选择题加“其他 / 无法判断”，或者先用一道是非题问“是否有答案”。
- **拆题。** 一个可核对的事实一道题。整体性的“这个好不好”远不如几道具体的是非题。
- **批量的是题目，不是条目。** 同一状态的多道题可以一次问；给 N 个候选排序时，每个候选单独判断，不要把 N 个候选塞进一道题。
- **是非题“是 = 执行”。** 不要让“是”表示“不执行”。
- **题目和阈值放在一处管理。** 改了措辞或阈值就重跑评估。
- **只记录判断结果。** 记录模型版本、概率、阈值、走了哪条路径；不记录原始个人数据，除非隐私政策允许。

## 常见的错误建议

出现下面这些，说明复核没做到位：

- 让模型判断“用户有没有权限”或直接放行危险操作；
- 让模型自动批准报销、封号、删除，绕过文档规定的人工环节；
- 让模型算 SLA 是否超时、金额是否超限；
- 把整段对话或整个仓库塞进状态，问“下一步该怎么办”；
- 把等级题的数值当成金额、概率或时长使用；
- 去掉合规要求保留的规则，而不是在规则之外补充判断；
- 没有调用量出处却写“每天节省 X 元”“提速 N 倍”。
